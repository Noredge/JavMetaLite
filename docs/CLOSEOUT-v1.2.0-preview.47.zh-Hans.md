# preview.47：平衡收尾报告（内部审核）

日期：2026-09-04

状态：本轮实现、离线性能对照、完整自动化和便携包校验已完成，等待用户试用；未推送或对外发布。优化前基线为本地提交 `152e7df`（preview.46）。保留 WPF、现有依赖、四语言资源字典、审核会话和文件事务设计。

## 实际完成的范围

- 队列：合并属性通知造成的昂贵刷新；全选/取消全选集中更新统计；当前影片切换不再重置整个列表。问题筛选仍会随 ID、搜索失败、来源失败和保存状态变化刷新。
- 导入：后台准备分组与去重，按 64 部一批载入**新建且未绑定界面的** MovieJob，在 UI 线程接管。局部分组索引不跨保存/重命名持久化，避免过期；完全重复的文件组不反复更新。保留全部本地图片校验、多 CD、取消和错误隔离。
- 图片：主界面预览解码宽度为 640（本地小图不放大），跨影片 LRU 最多 12 项、估计解码像素预算 32 MiB。该预算不等于整个进程内存上限；压缩字节、WPF/原生渲染及当前显示图另有开销。已有在线原始字节缓存仍保留。
- 查看器：不把主界面缩小的预览当成大图；独立载入最多 1600 宽的显示图并显示真实原始尺寸，尺寸/裁切处理在后台完成。保存与高清来源比较仍使用原图。
- 四语言：缓存原始宽高、显示时格式化，修复切语言后恢复旧提示；去除重复队列刷新；补齐扫描诊断的四语言摘要，技术原文留详情；缺失翻译回退英文并输出诊断。资源键集合保持一致（新增 3 个键后各 483 个），补占位符契约及实际格式化测试。没有翻译影片 metadata。
- 适度重构：提取 `QueueRefreshCoordinator`、`MovieQueueImport`、`MoviePreviewCache`、`ArtworkPreviewLoader` 和 `DiscoveryDiagnosticText`，让这些边界可直接测试。没有整体迁移 MVVM，没有只为减少行数搬代码。

## 实测方法

同一台机器、同一合成数据集，每个规模/场景独立建窗口并重复 3 次。主测试每版 126 条测量，模拟搜索每版 9 条。合成数据为零字节视频占位文件、最小 NFO、1600×1000 fanart、800×1000 poster、4 张 640×400 JPEG 样张，绝不读取真实影片库。图片是程序生成的测试图案。

记录导入/重复导入、全选/取消、筛选、连续浏览 48 部、语言切换的耗时、视图 Reset 次数、UI 输入优先级 10 ms 定时器的最长间隔、进程工作集和托管分配。强制 GC 在计时及分配测量**之后**执行，仅帮助比较保留内存。导入期间仍按设计禁止编辑，第一部可审核的时间包含全部导入和首张预览；没有改成边导入边编辑。

没有清空 OS 文件缓存，也没有宣称这些是严格冷启动、真实磁盘吞吐或帧率测试。三次数据包含首次与重复运行；JIT、文件缓存、Windows 定时器和渲染会影响结果。过程中构建工作可能带来噪声，关键结论同时依据确定的刷新次数和独立回归，不只看某一次秒数。多 CD、损坏文件、取消、部分来源失败在正确性测试覆盖，未为每种异常单独跑千片性能矩阵；没有添加侵入式逐次文件/解码计数器。

## 导入结果

| 规模 | 场景 | 导入前 → 后（秒） | 导入最大 UI 心跳间隔的中位数：前 → 后（毫秒） |
| --- | --- | --- | --- |
| 100 | 无 NFO/图片 | 0.169 → 0.185 | 161.6 → 62.6 |
| 100 | NFO + 封套 + 4 张样张 | 3.241 → 2.842 | 40.4 → 97.3 |
| 500 | 无 NFO/图片 | 0.396 → 0.461 | 393.9 → 58.9 |
| 500 | NFO + 封套 + 4 张样张 | 30.948 → 11.318 | 73.7 → 93.7 |
| 1000 | 无 NFO/图片 | 0.780 → 0.849 | 778.1 → 52.2 |
| 1000 | NFO + 封套 + 4 张样张 | 67.550 → 22.960 | 125.5 → 91.5 |

结论：图片密集场景总耗时明显降低，裸队列的长 UI 阻塞明显减少，但**并非每项操作都更快**。例如 100 部裸队列约 169 → 185 ms，100 部重复导入约 48 → 83 ms；后台调度和界面让步有开销。100/500 部图片队列单次 UI 心跳峰值反而有所增加，批次集中展示仍有约 100 ms 的峰值；不把本轮称为“所有操作无卡顿”。下一次若用户实际感到导入阶段顿挫，可优先对 UI 应用批次做时间预算，而不是增加磁盘并发。

## 交互与图片内存

- 1,000 部裸队列全选：中位数 **1202.95 → 2.81 ms**；整视图 Reset **2001 → 0**。
- 1,000 部带图片队列全选：中位数 **1304.33 → 3.87 ms**；Reset 同样为 0。这里的 0 是整视图重置，不代表不更新复选框和统计。
- 在 1,000 部带图片队列中连续浏览 48 部：约 **3.619 → 2.937 秒**；测量末尾进程工作集中位数约 **720 → 275 MiB**。这是包含整个测试进程的工作集，不是精确归因到某一个缓存的占用。
- 语言切换的队列 Reset 由通常 4 次减为 2 次（测试依次切到两种语言）；时长仍有波动，未宣称语言系统本身大幅提速。
- 缓存淘汰、再次载入、来源失效、本地删除、原图尺寸和四语言缓存恢复均有回归覆盖。

## 模拟搜索结果

实际点击批量搜索按钮，HTTP transport 固定返回测试 JSON，计划延迟 2 ms，保留默认影片并发度；Windows 实际定时器延迟并不保证正好 2 ms。每轮均断言 DMM 请求数等于影片数，R18 请求数为 0。

| 规模 | 模拟搜索前 → 后（秒，中位数） | 全队列 Reset 次数：前 → 后 |
| --- | --- | --- |
| 100 | 2.187 → 0.191 | 401 → 1 |
| 500 | 5.757 → 1.654 | 2001 → 1 |
| 1000 | 13.297 → 2.170 | 4001 → 1 |

1,000 部优化后实际三次为 1.949 / 2.170 / 3.889 秒，存在明显计时波动；不能将中位数倍数宣传成实际网站提速。网络等待、R18 限流和图片下载未包含在这个模拟结果中，没有提高任何网站请求并发或绕过限流。

搜索期间累计托管分配仍较高（千片约 7.35 → 2.06 GB；不是驻留内存），说明频繁统计仍有进一步改善空间。这是后续观察点，不在本轮追加一套复杂状态管理框架。
