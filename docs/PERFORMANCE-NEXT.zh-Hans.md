## 当前方向：DMM 优先，local database 暂缓

用户最新决定：DMM 是主要来源。preview.46 将 LibreDMM 设为默认推荐来源，移除原自动多来源选项，保留自定义多来源及 R18 单来源；批量模式明确提示 R18 限流或网络状况可能降低速度。R18 主要提供英文资料，以及部分影片更高分辨率的图片，不作为默认查询依赖。

当前不推进本地数据库。以下保留此前的候选设计以便未来讨论，不视为当前已批准的实施任务；本轮不新增高级离线选项、不安装数据库依赖、不下载完整 dump。Jellyfin 标题/标签翻译插件仅讨论可行性，不创建项目、不开发、不安装，也不扩展现有 Local Rating 插件。

- 在高级设置中提供默认关闭、标为实验性的离线 R18 数据选项；先验证可行性，不默认取代在线搜索，不随便携包附带完整数据库。
- 用用户明确选择的 dump/离线库建立本地只读查询路径，显示数据日期、路径、导入状态与失败原因。下载/更新由用户发起，不在启动时静默下载。
- 第一阶段验证 PostgreSQL dump 的必要字段与关联能否流式导入本地索引（候选方案 SQLite；不要求安装 PostgreSQL、不执行不受信任的任意 SQL）。保持 R18 来源身份、现有自定义字段规则与整套图片来源选择。
- 验证番号到 content_id 的准确命中、标题/演员等字段覆盖、图片链接可用性、导入时间/磁盘占用、冷/热查询速度和内存；用确定的数据样本再决定扩大范围。
- 未收录或快照过期可按明确策略回退在线请求，继续遵守 preview.44 限流；离线命中不代表图片已离线下载。取消或导入失败不能破坏上一个可用库。
- 是否开展高级选项原型与可行性验证，等待来源修复的使用反馈及后续讨论；不预设必然引入数据库。外部发布仍需单独批准。

## 目标与测量

以个人、本地使用为目标，不承诺未经测量的“千片秒开”。先记录同一台机器、同一数据集的优化前后结果：

- 用 100 / 500 / 1,000 部合成影片或获准的测试副本，分别测试无 NFO、已有 NFO/图片、多 CD、重复路径和损坏旁车；不要改动真实影片库。
- 导入：目录扫描、分组去重、本地读取、队列更新分别耗时；首个可操作界面时间、总导入时间、主线程最长停顿。
- 交互：导入期间取消、滚动和切片响应；全选/筛选耗时；工作集/分配量及图片缓存是否随全部影片数持续增长。
- 搜索：成功/单源失败/超时/取消/重试下的总耗时、每影片每来源请求数、实际并发数；区分网络等待、解析、图片预载和 UI 更新耗时。
- 先用确定延迟与失败的离线 provider fixture 排除网络噪声；少量真实在线检验只验证实际可用性，不用高并发压测外部网站。

首轮基线完成后再与用户确定验收阈值。当前 50 项 WPF 功能用例只证明队列行为与虚拟化存在，不能替代大队列性能基准。

## 优先检查的位置（候选，不是已证实瓶颈）

1. 影片发现与载入：`MovieInputDiscovery`、`MovieFileDiscovery`、`MainWindow` 导入流程。检查是否在 UI 线程连续进行目录/NFO/图片工作、是否重复扫描，以及是否可按批次更新队列。
2. 队列与图片：`MovieJob` 状态通知、`RefreshQueueUi`、WPF 虚拟化、影片预览缓存与查看器预载。检查无关行重绘、整队列刷新、全尺寸图片解码和切片时重复工作；保留有界缓存与取消能力。
3. 搜索：`BatchMetadataSearchCoordinator`、`MetadataSearchCoordinator`、provider clients 与图片来源分辨率比较。检查重复请求、失败重试范围、HTTP 复用、可取消等待及网络/图片任务之间的竞争。

## 优化边界

- 只修改测量证实有价值的热路径；保留现有 Core/App 分工、MovieJob 隔离与人工审核流程，不以优化为由全面重写 MVVM 或引入服务端。如果后续决定验证可选离线索引，也不扩展成通用媒体数据库。
- 不盲目提高当前受控并发，不绕过网站限制，不降低图片来源一致性或丢弃用户选择。
- 不牺牲保存预览、影片不覆盖、冲突检查、哈希校验、取消等待和回滚安全换速度。
- 已缓存的 SDK/依赖继续保留；不先做大规模依赖升级。

## 完成门槛

1. 可复现的前后对照记录，明确测试机器、数据集和缓存冷热条件。
2. 大队列导入/滚动/切片/取消实际验收；离线搜索效率与异常路径回归。
3. 完整自动化、便携包版本/哈希校验通过，再用获准的真实副本验证保存与影片字节。
4. 用户审核通过后，另行决定未来功能方向与外部发布；性能工作完成本身不代表发布授权。
